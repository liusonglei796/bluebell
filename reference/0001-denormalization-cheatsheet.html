Reference Sheet #0001

数据库反范式与冗余字段决策准则

核心原则：数据库范式保证写数据时的正确与无损；反范式冗余支撑高并发读请求的极速响应。

一、 4 步决策判断树

  1. 业务读写比（Read/Write Ratio）是否极度读多写少？
    • 读写比 > 10:1（如社区刷帖、电商商品展示） $\rightarrow$ 强烈考虑冗余。
    • 写多读少或频繁更新（如日志流水、传感器上报） $\rightarrow$ 坚决严禁冗余。
  2. 查询是否处于核心高频关键链路（P99 延迟敏感）？
    • 首页信息流、列表单卡片、高频聚合统计 $\rightarrow$ 必须避免多表 JOIN。
  3. 被冗余字段的“突变频率”与“修改代价”如何？
    • 几乎不改/天然不可变（如历史快照、订单生成时的商品标题与单价） $\rightarrow$ 完美冗余候选。
    • 频繁修改（如用户签名、用户动态余额） $\rightarrow$ 不宜冗余（会引发写放大与级联更新地狱）。
  4. 是否面临分库分表（Sharding）环境？
    • 跨表跨库无法发起物理 JOIN $\rightarrow$ 必须冗余 Sharding Key（如 `user_id` / `tenant_id`）。

二、 冗余字段分类速查表

分类 典型字段案例 冗余收益 一致性维护策略
1. 路由分片键 post_bookmark.user_id
comment.post_id		 避免广播全库，直达目标分片；支持单表主键/覆盖索引。 创建后不可变，无维护成本。
2. 历史快照数据 order_item.product_name
order_item.deal_price		 即便商品后续改名降价，订单仍保留当时交易快照。 只读业务属性，天然不可变。
3. 聚合计数器 post.comment_count
folder.post_count		 避免每次查询执行极其昂贵的 COUNT(*)。 本地事务原子自增/自减，配合定时异步离线对账校准。
4. 稳定展示属性 post.author_name
post.community_name		 列表渲染无需 JOIN 用户表与社区表。 改名时通过 MQ 领域事件异步批量刷新。
严禁冗余的红线区：
  • 强一致资产数据：用户账户可用余额、库存剩余数量（必须单点权威存储，避免脏读超卖）。
  • 大体量富文本：文章长内容、富媒体详情（会极大增加关联表的体积与单页行数限制）。
